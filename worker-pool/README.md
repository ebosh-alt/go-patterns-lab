# Worker Pool
> Паттерн относится к паттернам конкурентности.

Worker Pool ограничивает количество задач, которые выполняются одновременно. Вместо запуска отдельной горутины для каждой задачи создаётся фиксированный набор воркеров. Они получают работу из общей очереди и после выполнения берут следующую задачу.

Главная цель паттерна - сделать нагрузку на систему ограниченной и предсказуемой.

## Проблема

Запуск горутины для каждой входящей задачи выглядит просто, но не задаёт верхнюю границу параллельной работы.

Под нагрузкой ограничение обычно появляется за пределами самой программы:

- база данных допускает конечное число соединений;
- внешний API ограничивает частоту запросов;
- файловая система и сеть имеют ограниченную пропускную способность;
- каждая активная задача удерживает память и другие ресурсы.

Если новые задачи поступают быстрее, чем система успевает их завершать, количество одновременно работающих горутин и потребление ресурсов продолжают расти.

Worker Pool ставит между источником задач и их выполнением явный предел.

## Ограничение параллелизма

Количество воркеров задаёт верхнюю границу одновременно выполняемых задач. Если запущено пять воркеров, в один момент времени работу выполняют не более пяти задач, даже если в очереди их тысячи.

Размер пула не ускоряет отдельную операцию. Он определяет, сколько операций система разрешает выполнять одновременно.

Слишком маленький пул оставляет доступные ресурсы без работы. Слишком большой создаёт конкуренцию за CPU, соединения, память и внешние лимиты.

## Очередь и backpressure

Очередь отделяет скорость поступления задач от скорости обработки.

Небуферизованный канал передаёт задачу воркеру напрямую. Producer ждёт, пока один из воркеров будет готов принять работу.

Буферизованный канал позволяет временно накапливать задачи. Он сглаживает короткие пики, но не увеличивает пропускную способность воркеров.

Если размер очереди ограничен, заполненная очередь создаёт backpressure: отправитель блокируется, получает ошибку или отказывается от задачи по выбранной политике.

Неограниченное накопление скрывает перегрузку. Внешне система продолжает принимать работу, но задержка и потребление памяти растут.

## Как выбирать параметры

Универсальной формулы для размера пула нет.

Для CPU-bound задач отправной точкой может быть число доступных процессоров. Дальше размер проверяется измерениями, потому что результат зависит от характера вычислений и конкуренции с остальной программой.

Для I/O-bound задач воркеров часто больше, поскольку часть времени они ждут сеть или диск. Верхнюю границу обычно задаёт внешний ресурс: пул соединений базы данных, rate limit API, пропускная способность сети или допустимая задержка.

Размер очереди выбирается отдельно. Он отражает, какой кратковременный всплеск система готова принять и сколько дополнительной задержки допустимо накопить.

## Жизненный цикл

У пула должны быть понятны четыре состояния:

1. запуск воркеров;
2. приём задач;
3. прекращение приёма;
4. ожидание или отмена выполняющейся работы.

При graceful shutdown очередь закрывается, воркеры завершают уже принятые задачи и выходят, когда работа заканчивается.

При отмене задачи должны получить сигнал и остановиться сами.

Закрывать канал задач должен владелец пула. Несогласованное закрытие и отправка в закрытый канал приводят к ошибке.

## Результаты и ошибки

Ошибка внутри воркера не должна исчезать.

Контракт пула может возвращать:

- отдельный результат для каждой задачи;
- канал ошибок;
- агрегированную ошибку после завершения;
- отмену всего пула при первой ошибке.

Выбор зависит от сценария. Для независимых задач часто полезно собрать все результаты. Для связанной операции иногда правильнее отменить оставшуюся работу после первой ошибки.

Порядок результатов обычно не совпадает с порядком задач: более короткая задача завершится раньше, даже если была отправлена позже.

## Плюсы

- ограниченная степень параллелизма;
- предсказуемое потребление ресурсов;
- естественная точка для backpressure;
- переиспользование воркеров;
- единое управление запуском, отменой и завершением.

## Ограничения

- появляются очередь, состояния и отдельный жизненный цикл;
- неправильный размер пула снижает производительность;
- длинная очередь увеличивает задержку;
- зависшая задача удерживает воркер и уменьшает пропускную способность;
- порядок выполнения и результатов становится недетерминированным.

## Когда применять

Worker Pool подходит, если есть поток независимых задач и нужно ограничить параллельную нагрузку:

- обработка файлов;
- фоновые задания;
- запросы к базе данных или внешнему API;
- batch-операции;
- преобразование большого набора независимых элементов.

Паттерн может быть лишним, если задач мало, ограничение параллелизма не требуется или операция уже управляется внешним планировщиком.

## Типичные ошибки

- запуск нового пула для каждой задачи;
- отсутствие ограничения на очередь;
- игнорирование ошибок воркеров;
- отсутствие отмены и корректного завершения;
- закрытие канала из нескольких мест;
- отправка задачи в тот же заполненный пул из его воркера;
- изменение общих данных без синхронизации;
- выбор размера пула без измерений и учёта внешних лимитов.
