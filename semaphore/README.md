# Semaphore

Semaphore ограничивает количество операций, которые одновременно получают доступ к ресурсу. Перед началом работы операция захватывает разрешение, а после завершения возвращает его.

Пока свободные разрешения есть, новые операции проходят к ресурсу. Когда лимит исчерпан, следующие операции ждут освобождения места или завершают ожидание по отмене.

Главная цель семафора - не позволить параллельной нагрузке превысить реальную ёмкость защищаемого ресурса.

## Проблема

Количество горутин само по себе не отражает количество операций, которое выдерживает база данных, внешний API, файловая система или другой ресурс.

Приложение может легко создать сотни конкурентных операций, хотя ресурс способен стабильно обслуживать только несколько. В результате растут задержки, количество открытых соединений, потребление памяти и вероятность отказа.

Semaphore ставит перед ресурсом общий ограничитель. Горутины остаются независимыми, но одновременно критическую операцию выполняет не больше заданного числа участников.

## Структура

У паттерна четыре участника:
1. **Разрешение** описывает одну единицу доступной параллельности.
2. **Семафор** хранит общую ёмкость и состояние занятых разрешений.
3. **Горутина или операция** захватывает разрешение перед работой и освобождает после неё.
4. **Защищаемый ресурс** получает не больше одновременных операций, чем допускает лимит.

Семафор не хранит задачи и не выполняет их. Он управляет только правом доступа.

## Acquire и Release

`Acquire` резервирует разрешение. Если лимит уже исчерпан, операция ждёт.

`Release` возвращает ранее захваченное разрешение и позволяет продолжить работу одному из ожидающих участников.

Между этими операциями должна сохраняться симметрия:

- каждый успешный `Acquire` требует одного соответствующего `Release`;
- `Release` без захвата нарушает состояние семафора;
- забытый `Release` уменьшает доступную ёмкость и может заблокировать систему.

Освобождение обычно регистрируют через `defer` сразу после успешного захвата.

## Backpressure и ожидание

Когда разрешения заканчиваются, семафор создаёт backpressure. Новая операция не попадает к ресурсу, пока одна из активных не завершится.

Ожидание должно уметь завершаться по `context.Context`, если операция связана с запросом, дедлайном или отменяемой фоновой задачей. Без отмены горутина может ждать разрешение дольше, чем результат её работы остаётся нужен.

Semaphore ограничивает одновременное выполнение, но не ограничивает скорость операций за период времени. Для ограничения запросов в секунду нужен Rate Limiter.

## Разновидности

### Бинарный семафор

Имеет одно разрешение. В каждый момент ресурс использует только один участник.

По поведению он похож на Mutex, но назначение отличается. Mutex обычно защищает инварианты общих данных и имеет понятие критической секции. Семафор управляет доступной ёмкостью ресурса.

### Считающий семафор

Содержит несколько одинаковых разрешений. Каждая операция занимает одно место независимо от своей стоимости.

В Go простую реализацию можно построить на буферизованном `chan struct{}`. Ёмкость канала задаёт максимальное количество одновременных владельцев.

### Взвешенный семафор

Операции занимают разное число разрешений. Лёгкая задача может запросить вес 1, тяжёлая - вес 4.

Взвешенный вариант полезен, когда одинаковое количество операций создаёт разную нагрузку на память, CPU или внешний ресурс.

## Как выбирать лимит

Лимит должен отражать ограничение защищаемого ресурса, а не количество задач в приложении.

Для базы данных отправной точкой может быть доступный пул соединений. Для внешнего API учитываются допустимый параллелизм и поведение сервера. Для файловых операций измеряются задержка и пропускная способность диска. Для памяти оценивается стоимость одной активной операции.

Слишком маленький лимит оставляет ресурс недогруженным. Слишком большой перестаёт защищать его от перегрузки.

Значение проверяется нагрузочными тестами и метриками:

- длительность ожидания разрешения;
- количество ожидающих операций;
- время работы защищаемого ресурса;
- ошибки и таймауты;
- фактический параллелизм.

## Владение и область действия

Все части приложения, которые конкурируют за один ресурс, должны использовать один и тот же семафор.

Если каждый компонент создаёт собственный ограничитель с лимитом 10, общий ресурс может получить значительно больше десяти одновременных запросов.

Владелец семафора должен определять:

- где он создаётся;
- кто использует общий экземпляр;
- какой ресурс он защищает;
- кто отвечает за изменение лимита и наблюдаемость.

## Порядок ожидания

На семафор нельзя полагаться как на строгую очередь с гарантированным порядком обслуживания, если такая гарантия явно не реализована.

Одни операции могут ждать дольше других. Во взвешенном семафоре крупная операция может задерживаться, если свободной ёмкости хватает только для более лёгких задач.

Если порядок и справедливость критичны, их нужно проектировать отдельно.

## Плюсы

- ограничение одновременной нагрузки;
- общий лимит для разных частей приложения;
- естественный backpressure перед ресурсом;
- простое отделение конкурентного выполнения от ёмкости ресурса;
- поддержка операций разной стоимости во взвешенном варианте.

## Ограничения

- неправильный лимит снижает производительность или не защищает ресурс;
- потерянное разрешение может заблокировать ожидающие горутины;
- семафор не управляет очередью задач и жизненным циклом горутин;
- ожидание без context может стать бесконечным;
- один семафор не ограничивает количество операций за единицу времени.

## Сравнение с другими механизмами

### Semaphore и Worker Pool

Worker Pool управляет фиксированным набором горутин и распределяет между ними задачи. Semaphore не создаёт воркеры и не хранит задачи. Он ограничивает доступ уже существующих горутин к конкретному ресурсу.

### Semaphore и Mutex

Mutex допускает одного владельца и обычно защищает общее состояние. Считающий семафор допускает несколько владельцев и моделирует доступную ёмкость.

### Semaphore и Rate Limiter

Semaphore ограничивает число одновременных операций. Rate Limiter ограничивает число операций за интервал времени.

## Когда применять

Semaphore подходит для ограничения:

- запросов к базе данных;
- обращений к внешнему API;
- файловых операций;
- задач с высоким потреблением памяти;
- параллельной обработки рядом с ограниченным внешним ресурсом.

Он может быть лишним, если ограничение уже обеспечивает Worker Pool, драйвер ресурса или внешний планировщик.

## Типичные ошибки

- `Acquire` без гарантированного `Release`;
- `Release` после неуспешного захвата;
- ожидание без context и дедлайна;
- отдельный семафор в каждом компоненте для одного общего ресурса;
- лимит, выбранный без измерений;
- повторный захват всех разрешений одной горутиной;
- использование семафора вместо Rate Limiter;
- ожидание строгого порядка выполнения.
