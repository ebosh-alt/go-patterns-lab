# Паттерн Цепочка обязанностей
> Также известен как: CoR, Chain of Command, Chain of Responsibility
___
## Идея
Передавать запрос последовательно по цепочке обработчиков. Каждый обработчик решает: **обработать** запрос или **передать дальше**.
___
## Когда применять

- Набор проверок/реакций меняется со временем или конфигурируется.
- Отправитель не должен знать, **кто** обработает запрос.
- Нужно выстроить **последовательность фильтров/валидаторов**.
- Хотите переиспользуемые и независимые блоки логики (middleware).
___
## Плюсы

- Слабая связанность
- Гибкая конфигурация
- Простое добавление новых звеньев
- Удобное тестирование по частям.
___
## Минусы

- Возможна «протечка» до конца без обработки
- Сложнее дебаг цепочки
- Порядок критичен.
___
## Структура

- Handler (интерфейс): `handle(request)` и ссылка на `next`.
- BaseHandler (опционально): хранит `next`, дефолтно делегирует.
- ConcreteHandler: решает обработать/делегировать.
- Client: собирает цепь и передаёт запрос в первое звено.

## Шаги внедрения

1. Определите **формат запроса** и исходы (успех/ошибка/делегирование).
2. Введите базовый обработчик с `next` и единый интерфейс.
3. Разбейте логику на независимые обработчики (валидация, аутентификация, кеш/лимитер, бизнес).
4. Сборка цепи: конструктор/DI, конфиги и флаги — чтобы переставлять звенья без перекомпиляции.
5. Тесты: на каждый обработчик отдельно + интеграционный тест цепочки.
___
## Варианты и приёмы

- Терминатор: последний обработчик, гарантирует ответ (иначе 5xx/исключение).
- Разветвление: внутри обработчика можно разветвлять дальше (компоновка нескольких цепей).
- Кэш/короткое замыкание: early return для быстрых путей.
- Логирование трассы: корреляционный id, чтобы видеть путь запроса.
___
## Типичные ошибки

- Неявный порядок звеньев → сделать явным в коде/конфиге.
- «Всесильные» обработчики с побочными эффектами → принцип единой ответственности.
- Отсутствие финального обработчика → «зависание» запроса.
___
## Где хорошо ложится

- Веб‑серверы и RPC (middleware/interceptors).
- Боты/обработчики событий.
- ETL/конвейеры данных
___
## Чек‑лист перед применением

-  Ясна ли цель каждого звена?
- Зафиксирован ли порядок и контракты?
- Есть ли быстрый «короткий путь»?
- Как логируете и тестируете цепочку?
- Можно ли менять состав без правок бизнес‑кода?
